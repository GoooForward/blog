# 0x00 什么是系统编程

Linux 系统编程是指在 Linux 操作系统环境下，编写直接与操作系统内核交互的程序，以充分利用 Linux 的底层功能和服务。这种编程方式通常涉及调用 Linux 内核提供的系统调用（System Calls）和使用各种系统库，来实现对硬件、文件系统、进程、内存、网络等资源的直接控制和管理。

### 核心特点

1. **直接操作内核功能**：Linux 系统编程的核心是通过系统调用（如`open`、`read`、`write`、`fork`、`exec`等）直接请求内核提供服务，而不是依赖高级语言的抽象层（如 C++ 的`std::fstream`或 Python 的`os`模块，这些本质上也是对系统调用的封装）。

2. 面向底层资源管理

    ：关注操作系统的核心资源，包括：

    - **进程管理**：创建、终止进程，进程间通信（IPC），线程管理等。
    - **文件系统**：操作文件、目录，权限控制，磁盘 I/O 等。
    - **内存管理**：动态内存分配（`malloc`底层依赖`sbrk`或`mmap`系统调用），内存映射等。
    - **网络编程**：使用套接字（socket）进行网络通信，实现 TCP/UDP 协议等。
    - **设备驱动**：与硬件设备交互（虽然驱动开发更接近内核编程，但系统编程也会涉及设备文件的操作）。

3. **依赖 C 语言和系统库**：传统上，Linux 系统编程主要使用 C 语言（因为 Linux 内核和系统库主要用 C 编写），但也可以用 C++、Rust 等语言通过调用系统库或直接触发系统调用来实现。

4. **需要了解 Linux 内核机制**：开发者需要熟悉 Linux 的内核架构、进程模型、文件系统层次、权限模型等底层原理，才能正确、高效地使用系统调用。

# 0x01 系统调用和库函数

## 什么是系统调用？

你可以把系统调用理解为 **“用户程序向内核请求服务的接口”**。

- 用户空间与内核空间：现代操作系统为了安全和稳定，将程序的运行空间分为两部分：

    - **用户空间（User Space）**：普通应用程序运行在这里。这个空间的程序权限较低，不能直接访问硬件资源（如内存、磁盘、CPU），也不能执行特权指令。
    - **内核空间（Kernel Space）**：操作系统内核运行在这里。内核拥有最高权限，可以直接控制硬件、管理内存、调度进程等。
    
- **跨越边界**：当一个用户程序需要执行一项它没有权限直接完成的任务时（比如读取一个文件、创建一个新进程、发送网络数据），它就必须通过某种方式 “请求” 内核来帮它完成。这个 “请求” 的过程，就是通过 **系统调用** 来实现的。

简单来说，**系统调用就是用户程序从用户空间进入内核空间的 “门”**。

### 系统调用的工作流程

一个系统调用的执行通常遵循以下步骤：

1. **应用程序调用库函数**：程序员在代码中调用一个标准库函数，例如 `printf()` 或 `open()`。
2. **库函数封装系统调用**：这个库函数（比如 C 标准库中的函数）会将系统调用的编号和参数准备好，然后执行一个特殊的 CPU 指令（如 `int 0x80` 或 `syscall`）。这个指令会触发一个 **软中断（Software Interrupt）**。
3. **CPU 切换到内核态**：CPU 收到中断信号后，会暂停当前用户程序的执行，保存其上下文（寄存器状态等），然后切换到 **内核态（Kernel Mode）**。
4. **内核处理系统调用**：内核根据预先定义好的系统调用编号，找到对应的内核函数（称为 “系统调用处理程序”）并执行它。这个内核函数会完成真正的底层操作，比如与硬件交互。
5. **返回结果**：内核函数执行完毕后，会将结果返回给系统调用处理程序，处理程序再将结果存入指定的寄存器，并恢复之前保存的用户程序上下文。
6. **CPU 切换回用户态**：CPU 切换回 **用户态（User Mode）**，并从之前暂停的地方继续执行用户程序。
7. **库函数返回结果**：库函数从寄存器中取出结果，可能进行一些简单的处理（比如设置 `errno` 变量来表示错误），然后将最终结果返回给应用程序。

这个过程对程序员来说是 **透明的**，你只需要调用库函数即可，无需关心底层的切换和内核处理细节。

### 常见的 Linux 系统调用分类

Linux 提供了数百个系统调用，它们可以被大致分为以下几类：

1. **进程管理**：
    - `fork()`: 创建一个新进程。
    - `execve()`: 在当前进程中执行一个新程序。
    - `exit()`: 终止当前进程。
    - `wait()`: 等待子进程结束。
    - `getpid()`: 获取当前进程的 ID。
2. **文件 I/O**：
    - `open()`: 打开或创建一个文件。
    - `close()`: 关闭一个文件。
    - `read()`: 从文件中读取数据。
    - `write()`: 向文件中写入数据。
    - `lseek()`: 移动文件读写指针。
    - `stat()`: 获取文件的状态信息。
3. **内存管理**：
    - `brk()` / `sbrk()`: 调整进程的数据段大小（`malloc` 底层会用到）。
    - `mmap()`: 将文件或设备映射到内存地址空间。
    - `munmap()`: 解除内存映射。
4. **进程间通信 (IPC)**：
    - `pipe()`: 创建一个管道，用于父子进程间通信。
    - `msgget()` / `msgsnd()` / `msgrcv()`: 消息队列。
    - `shmget()` / `shmat()` / `shmdt()`: 共享内存。
    - `semget()` / `semop()`: 信号量。
5. **网络通信**：
    - `socket()`: 创建一个套接字。
    - `bind()`: 将套接字绑定到一个地址和端口。
    - `listen()`: 监听套接字上的连接。
    - `accept()`: 接受一个连接。
    - `connect()`: 发起一个连接。
    - `send()` / `recv()`: 发送和接收数据。
6. **信号处理**：
    - `signal()`: 设置一个信号的处理函数。
    - `kill()`: 向一个或多个进程发送信号。

## 什么是库函数

在 Linux 系统编程和软件开发中，**库函数（Library Function）** 是封装了特定功能、可被多个程序复用的代码模块，由编译器、操作系统或第三方提供，位于用户空间，是对底层逻辑（如系统调用、基础算法）的高层抽象。

简单来说，库函数是 **“程序员的工具包”** —— 它把常用功能（如文件读写、字符串处理、数学计算）提前实现好，让开发者无需重复编写底层代码，直接调用即可完成任务，既提高开发效率，又保证代码的稳定性和兼容性。

### 一、库函数的核心本质

1. **用户空间的 “封装层”**

    库函数运行在 **用户空间**（而非内核空间），权限与普通应用程序一致。它的核心价值是 “隐藏复杂度”：

    - 若功能依赖内核服务（如文件读写），库函数会**封装系统调用**（比如 C 标准库的 `fopen` 底层调用内核的 `open` 系统调用），并处理参数校验、错误封装（如将 `errno` 转换为更易读的错误信息）、缓冲区管理等细节。
    - 若功能不依赖内核（如字符串复制 `strcpy`、数学计算 `sqrt`），库函数则是纯粹的用户态逻辑，直接在用户空间执行，无需切换到内核态。

2. **可复用的 “模块化代码”**

    库函数被编译成二进制文件（库文件），多个程序可同时调用，无需在每个程序中重复编译相同代码（比如所有 C 程序都能调用 `printf`，无需自己实现 “向终端输出字符” 的逻辑）。

### 三、库函数的分类（按功能和链接方式）

#### 1. 按功能分类（常用）

- **C 标准库（libc）**：最基础、最常用的库函数，所有 C 程序都可使用，由 ISO C 标准定义，跨平台兼容性强。

    核心功能：

    - 字符串处理：`strcpy`、`strlen`、`strcmp`（字符串复制、长度计算、比较）；
    - 输入输出：`printf`、`scanf`、`fopen`、`fread`（格式化输入输出、文件流操作）；
    - 数学计算：`sqrt`（平方根）、`sin`（正弦）、`abs`（绝对值）；
    - 内存管理：`malloc`、`free`、`memcpy`（动态内存分配、内存复制）；
    - 错误处理：`perror`、`strerror`（打印错误信息）。

- **POSIX 库**：遵循 POSIX 标准的系统级库函数，主要用于 Linux/Unix 系统编程，部分封装系统调用。

    核心功能：

    - 进程 / 线程管理：`pthread_create`（创建线程）、`waitpid`（等待子进程）；
    - 进程间通信：`pipe`（管道）、`shmget`（共享内存）、`sem_init`（信号量）；
    - 网络编程：`socket`、`bind`、`listen`（套接字操作）；
    - 信号处理：`pthread_sigmask`（线程信号屏蔽）。

- **第三方库**：开发者或组织提供的功能扩展库，需手动安装后使用。

    典型例子：

    - Boost：C++ 扩展库（提供容器、算法、网络、多线程等高级功能）；
    - OpenSSL：加密库（提供 SSL/TLS 协议、哈希、签名等功能）；
    - SQLite：嵌入式数据库库（无需独立服务，直接操作本地数据库文件）；
    - Libcurl：网络请求库（支持 HTTP/HTTPS/FTP 等协议的请求发送）。

#### 2. 按链接方式分类（Linux 下的库文件类型）

库函数的物理载体是 “库文件”，Linux 下主要分两类，链接方式不同，影响程序编译和运行：

- **静态库（Static Library）**：
    - 文件名格式：`libxxx.a`（如 `libc.a` 是 C 标准静态库）；
    - 链接过程：编译时，编译器会将程序调用的库函数代码**直接复制到可执行文件中**；
    - 运行特性：可执行文件不依赖外部库文件，单独运行即可，但文件体积较大；若库更新，需重新编译程序。
- **动态库（Dynamic Library/Shared Library）**：
    - 文件名格式：`libxxx.so`（如 `libc.so` 是 C 标准动态库）；
    - 链接过程：编译时，编译器仅在可执行文件中记录 “依赖哪个动态库、哪个函数”，不复制库代码；
    - 运行特性：程序运行时，操作系统的动态链接器（`ld-linux.so`）会加载所需动态库到内存，多个程序可共享同一库的内存副本，因此可执行文件体积小，库更新后无需重新编译程序（兼容性需保证）。

**实际使用**：Linux 系统默认优先使用动态库（节省磁盘空间和内存），只有在需要 “程序独立运行、不依赖系统库版本” 时（如嵌入式设备），才会使用静态库。

### 四、库函数的调用流程（以 C 标准库 `fopen` 为例）

以 “打开文件” 为例，看库函数如何封装系统调用，简化开发：

1. 开发者编写代码：`FILE* fp = fopen("test.txt", "r");`（调用库函数 `fopen`）；
2. 库函数`fopen`执行逻辑：
    - 校验参数（如文件名是否为空、打开模式是否合法）；
    - 调用内核的 `open` 系统调用（请求内核打开文件）；
    - 若系统调用成功，创建 `FILE` 结构体（封装文件描述符、缓冲区、读写指针等）；
    - 若系统调用失败，设置 `errno`，并返回 `NULL`；
3. 开发者接收返回值：判断 `fp` 是否为 `NULL`，若失败则用 `perror("fopen")` 打印错误（库函数 `perror` 会解析 `errno` 为人类可读信息）。整个过程中，开发者无需关心：

- 系统调用 `open` 的参数格式（如文件权限位、标志位 `O_RDONLY`）；
- 内核返回的文件描述符（`open` 返回 `int` 型文件描述符，`FILE` 结构体已封装）；
- 缓冲区管理（`fopen` 会创建用户态缓冲区，减少 `read`/`write` 系统调用的次数，提升效率）。

## 系统调用与库函数的区别

| 特性         | 库函数（Library Function）                                   | 系统调用（System Call）                          |
| ------------ | ------------------------------------------------------------ | ------------------------------------------------ |
| **实现主体** | 编译器（如 GCC 的 C 标准库）、第三方开发者（如 Boost）       | 操作系统内核（Linux 内核开发者）                 |
| **运行空间** | 用户空间（User Space）                                       | 内核空间（Kernel Space）                         |
| **调用方式** | 普通函数调用（直接跳转指令，无模式切换）                     | 触发软中断（如 `syscall` 指令），需切换内核态    |
| **本质依赖** | 可依赖系统调用，也可纯用户态实现（如 `strlen`）              | 内核直接提供的底层服务，是操作系统的核心接口     |
| **开销**     | 低（仅函数调用开销，无上下文切换）                           | 高（需保存用户态上下文、切换内核态、恢复上下文） |
| **错误处理** | 通常返回特定值（如 `NULL`），或通过库函数（如 `perror`）处理 | 通过全局变量 `errno` 返回错误码，需手动检查      |
| **典型例子** | `fopen`、`fread`、`strcpy`、`printf`、`sqrt`                 | `open`、`read`、`write`、`fork`、`mmap`          |

**关键结论**：

库函数是对系统调用的 “包装 + 扩展”，或独立实现的基础功能。比如：

- `printf`（库函数）：底层调用 `write` 系统调用向终端输出，但额外处理了格式化字符串（如 `%d`、`%s`）、缓冲区刷新等逻辑；
- `fopen`（库函数）：底层调用 `open` 系统调用打开文件，但额外管理了文件流（`FILE*` 指针）、缓冲区（减少频繁系统调用，提升效率）。

**总结一下**：

- **系统调用**是底层的、由内核提供的 “原子操作”。
- **库函数**是建立在系统调用之上的，为了方便程序员使用而提供的更高层次的抽象。它可能调用一个或多个系统调用，也可能完全不调用（比如 `strcpy` 函数）。



# 0x02从源代码到系统调用

为什么在源码中使用open()就能调用系统调用，这中间隐藏了什么细节呢？

实际上，源码和系统调用中间隔着glibc，当用户调用open()函数时，实际链接到的是libc库中对应的open系统调用的包装函数。包装函数本质是：**一个用户态的 “代理函数”，负责参数校验、格式转换和系统调用触发**。它屏蔽了底层 CPU 架构和内核调用的细节，让开发者可以像调用普通函数一样使用系统调用。

> sysdeps/unix/sysv/linux/open.c

```c
/*
 * 这些是必要的头文件包含：
 * - sys/types.h, sys/stat.h, fcntl.h: 定义了 open 函数的参数类型（如 mode_t）、
 *   打开标志（如 O_RDWR, O_CREAT）和函数原型。
 * - stdarg.h: 提供了处理可变参数列表的宏（va_start, va_arg, va_end）。
 */
#include <sys/types.h>
#include <sys/stat.h>
#include <fcntl.h>
#include <stdarg.h>

#include <sysdep-cancel.h>

#ifndef __OFF_T_MATCHES_OFF64_T

/*
 * __libc_open: 这是 open 函数的内部实现函数。
 * - 它不是直接暴露给用户的符号，而是通过弱别名机制让用户代码可以调用。
 * - 参数:
 *   - file: 要打开或创建的文件路径名。
 *   - oflag: 打开文件的标志（如 O_RDONLY, O_WRONLY, O_RDWR, O_CREAT, O_TRUNC 等）。
 *   - ...: 可变参数，当 oflag 中包含 O_CREAT 或 O_TMPFILE 时，
 *          必须提供第三个参数 mode，表示新文件的权限位。
 */
int
__libc_open (const char *file, int oflag, ...)
{
  int mode = 0;

  if (__OPEN_NEEDS_MODE (oflag))
    {
      va_list arg;
      va_start (arg, oflag);
      mode = va_arg (arg, int);
      va_end (arg);
    }

  /*
   * SYSCALL_CANCEL (openat, AT_FDCWD, file, oflag, mode):
   * 这是整个函数的核心，它触发一个可被取消的系统调用。
   *
   * - openat: 这是要调用的系统调用名称。现代 glibc 倾向于使用 openat 而非 open，
   *   因为它更灵活（支持相对路径和 AT_FDCWD）。
   * - AT_FDCWD: 第一个参数，表示使用当前工作目录作为基准目录。
   *             结合 file 参数（绝对或相对路径），这使得 openat 的行为与传统的 open 完全相同。
   * - file, oflag, mode: 后续的参数直接传递给 openat 系统调用。
   *
   * SYSCALL_CANCEL 宏会处理所有底层细节：
   *   1. 将系统调用号和参数加载到正确的寄存器中。
   *   2. 执行触发系统调用的指令（如 x86_64 的 syscall）。
   *   3. 检查返回值，如果是 -ERESTART_RESTARTBLOCK (-4095)，则处理线程取消。
   *   4. 返回系统调用的结果。
   */
  return SYSCALL_CANCEL (openat, AT_FDCWD, file, oflag, mode);
}

/*
 * libc_hidden_def (__libc_open):
 * 这是一个 glibc 内部宏，用于将 __libc_open 符号隐藏在动态库中。
 * 这意味着外部程序不能直接链接到 __libc_open，只能通过别名访问。
 * 这是一种封装和版本控制的手段。
 */
libc_hidden_def (__libc_open)

/*
 * weak_alias (__libc_open, __open):
 * 创建一个名为 __open 的弱别名，它指向 __libc_open。
 * “弱”意味着如果用户代码中也定义了一个 __open 函数，链接器会优先使用用户的版本。
 */
weak_alias (__libc_open, __open)

/*
 * libc_hidden_weak (__open):
 * 将弱别名 __open 也隐藏起来。
 */
libc_hidden_weak (__open)

/*
 * weak_alias (__libc_open, open):
 * 创建一个名为 open 的弱别名，它指向 __libc_open。
 * 这是用户代码实际调用的符号。当你写 open(...) 时，链接器会找到这个别名，
 * 并最终指向 __libc_open 函数。
 */
weak_alias (__libc_open, open)
#endif
```

glibc源码内部，将open()函数将系统调用封装了起来，并且open()函数实际调用的是openat系统调用（此系统调用可以处理相对路径）。

而对于不同的架构的soc，openat的系统调用号也不同:

- **x86_64 (64 位 Intel/AMD)**：`openat` 的系统调用号是 **257**。
- **ARM (32 位)**：`openat` 的系统调用号是 **322**。
- **AArch64 (64 位 ARM)**：`openat` 的系统调用号是 **56**。

这样也屏蔽了不同架构带来的区别
