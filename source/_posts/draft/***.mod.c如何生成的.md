`.mod.c` 文件是 **内核模块编译过程中自动生成的中间文件**，核心作用是 **记录模块的依赖关系、符号信息和初始化 / 清理函数的元数据**，为内核加载模块提供关键信息。以下是其生成机制的详细解析：

### 一、核心结论

`.mod.c` 文件由 **内核构建系统（Kbuild）** 自动生成，生成触发条件是：当你编译一个内核模块（`.ko` 文件）时，Kbuild 会通过内置的脚本和规则，根据模块的源代码（如 `xxx.c`）、模块配置（`Makefile`）以及内核的符号表，动态生成对应的 `xxx.mod.c` 文件。

### 二、生成时机与触发流程

内核模块的编译流程（简化版）：

```plaintext
xxx.c（模块源码） + Makefile（模块编译规则）
        ↓
预处理、编译 → xxx.o（目标文件）
        ↓
Kbuild 生成 xxx.mod.c → 编译 xxx.mod.c 为 xxx.mod.o
        ↓
链接 xxx.o + xxx.mod.o → xxx.ko（最终内核模块）
```

关键触发步骤：

1. 你执行 `make` 编译模块时，Kbuild 会读取模块的 `Makefile`（通常包含 `obj-m += xxx.o` 等规则）；
2. Kbuild 会先编译 `xxx.c` 生成 `xxx.o`；
3. 此时 Kbuild 会自动调用 **内核自带的脚本**（`scripts/mod/modpost` 等），分析 `xxx.o` 中的符号、依赖，并结合内核的符号表（`Module.symvers`），生成 `xxx.mod.c`；
4. 接着 Kbuild 会编译 `xxx.mod.c` 生成 `xxx.mod.o`；
5. 最后将 `xxx.o` 和 `xxx.mod.o` 链接为最终的 `xxx.ko` 模块文件。

### 三、`.mod.c` 文件的核心内容（what's inside?）

`.mod.c` 是一个自动生成的 C 语言源文件，核心内容包括 3 部分，这些信息都是内核加载模块时必需的：

#### 1. 模块依赖关系声明

记录当前模块依赖的其他内核模块（即 `depends` 字段），对应 `modinfo xxx.ko` 看到的 `depends` 信息。

示例代码：

```c
#include <linux/module.h>
MODULE_INFO(depends, "dep_module1,dep_module2");  // 依赖的模块列表
```

作用：内核加载时，会先加载这些依赖模块，确保模块运行所需的符号和功能存在。

#### 2. 模块符号导出声明

记录当前模块向内核导出的符号（即 `EXPORT_SYMBOL` 或 `EXPORT_SYMBOL_GPL` 声明的函数 / 变量），对应 `modinfo xxx.ko` 看到的 `srcversion` 等信息。

示例代码：

```c
MODULE_INFO(srcversion, "ABC1234567890");  // 符号的校验和（用于版本匹配）
```

作用：内核通过符号校验确保模块与内核版本兼容，避免因符号不匹配导致的崩溃。

#### 3. 模块初始化 / 清理函数的 “包装”

将模块的 `init_module`（初始化函数）和 `cleanup_module`（清理函数）包装成内核可识别的格式，同时记录模块的元数据（如模块名、作者、许可证等）。

示例代码：

```c
static const struct modversion_info ____versions[]
__used __section(__versions) = {
    {0x12345678, "module_layout"},  // 内核模块布局的版本标识
    {0xabcdef01, "printk"},         // 依赖的内核函数（printk）的版本标识
    // ... 其他依赖符号的版本信息
};

MODULE_INFO(vermagic, "5.15.0-78-generic SMP mod_unload modversions ");  // 内核版本魔法值
```

作用：内核通过 `vermagic` 和 `____versions` 验证模块与内核的兼容性（如内核版本、SMP 配置、是否支持模块卸载等），只有匹配时才允许加载。

### 四、生成的核心工具：`modpost` 脚本

`.mod.c` 的生成不是由 GCC 直接完成的，而是由内核构建系统中的 **`modpost` 脚本**（位于 `scripts/mod/modpost.c`）负责，其工作流程：

1. 读取模块的目标文件（`xxx.o`），解析其中的符号（导出的、未定义的）；
2. 读取内核的符号表（`Module.symvers`，记录内核及其他模块导出的符号）；
3. 对比模块的未定义符号与内核符号表，确定模块的依赖关系；
4. 计算符号的校验和（`srcversion`）和内核版本魔法值（`vermagic`）；
5. 根据以上信息，生成 `xxx.mod.c` 文件，包含依赖声明、符号校验、版本信息等。

### 五、关键注意点

1. **自动生成，无需手动修改**：`.mod.c` 是编译过程的中间产物，由 Kbuild 自动生成，用户无需手动编写或修改（修改后会被下次编译覆盖）；
2. **与 `Module.symvers` 强相关**：`modpost` 脚本需要读取 `Module.symvers`（内核或上一级目录生成的符号表）来解析依赖，因此编译模块时必须确保 `Module.symvers` 存在（否则会导致依赖解析失败）；
3. **影响模块加载的兼容性**：`.mod.c` 中的 `vermagic`、`srcversion` 等信息是内核验证模块兼容性的关键，若模块编译时的内核配置（如 SMP、`CONFIG_MODVERSIONS`）与运行时内核不一致，会导致加载失败（提示 `invalid module format`）；
4. **编译后可删除**：`.mod.c` 是中间文件，编译生成 `xxx.ko` 后，可通过 `make clean` 删除（不会影响 `xxx.ko` 的使用，因为 `xxx.ko` 已包含 `.mod.c` 的信息）。

### 总结

`.mod.c` 是内核模块编译的 “桥梁” 文件，由 Kbuild 的 `modpost` 脚本根据模块源码、依赖和内核符号表自动生成，核心作用是 **记录模块的依赖关系、符号校验和版本兼容性信息**，确保模块能被内核正确加载和运行。它是内核模块编译流程中不可或缺的中间产物，但无需用户手动干预。
